# Protocol v0.1.0

The contract between room devices, staff devices, and the server. It is the written form of `development-plan.md` §3 (architecture) and §7.4 (contract sprint), with the decisions of 2026-10-01 applied.

Machine-readable twin: [`contracts/openapi.json`](../contracts/openapi.json) (generated from `server/app/protocol/models.py`). Constants live in `server/app/protocol/constants.py`. Timer test cases: [`contracts/timer-fixtures/`](../contracts/timer-fixtures/). If this document and the code disagree, **the fixtures win for timer behavior, the OpenAPI file wins for field names**, and the disagreement is a bug to fix here.

## 0. Status and change rules

- **Status:** v0.1.0, accepted by the PM on 2026-10-01. Scope: everything Phase 1 needs, plus the structures that are expensive to change later (command envelope, snapshot, merge rules, constants). Features not listed in §12 are *not* in v0.
- **Who can change it:** no approval gate (PM decision, ADR 0003). Instead:
  1. Bump `PROTOCOL_VERSION` in `constants.py` (additive change → minor, breaking → major).
  2. Add a line to the changelog (§14).
  3. Re-export `contracts/openapi.json`; update or add fixtures if timer behavior changes.
  4. Tell the owners of the other side (Ian: `server/`, `sync-core`; Forrest: `web/apps`, `e2e/`) in the PR description.
- **Breaking change** = removing/renaming a field, changing meaning, changing a constant that clients depend on. Prefer adding.

## 1. Conventions

- JSON, `snake_case` keys. Enum *values*: timer statuses and event types are `UPPER_CASE` (as in the spec); everything else is `lower_snake_case`.
- **Times are integer milliseconds of server time** (Unix epoch ms from the server's clock). Device clocks are never trusted (§4).
- Ids (`room_id`, `session_id`, `event_id`, `account_id`) are opaque strings up to 64 chars. `command_id` and `device_id` are UUIDs generated by the client.
- Every request and response body is a model in `openapi.json`. Unknown fields in requests are rejected.
- Server-originated errors use `ErrorResponse {error, message}` (§6.5).

## 2. Concepts

- A **room** always has one **current session** (one room running one test). Sessions are created by seed/admin tooling in v0 (§12); the protocol only reads and drives them.
- A session has an append-only **event list**; its state is a **fold** of that list (§5). Clients and server compute the same fold.
- A room's **version** is an integer that increases every time the room's snapshot changes. Clients ignore any snapshot whose version is lower than the one they hold.
- **Roles**
  - *Room devices* log in as a room, on a **surface**: `display` (read-only) or `control` (can send start/pause/resume).
  - *Staff* log in with a named account: `admin`, `pm`, or `to`. In v0 only `admin` and `pm` can send commands; `to` can log in and view (clarifications arrive in a later version).

## 3. Authentication

All auth endpoints are served by the server itself (invariant 6: no email, no OAuth).

| Endpoint | Purpose |
|---|---|
| `GET /api/auth/rooms?practice=false` | Login dropdown. **No auth.** Returns `{event_id, event_name, rooms: [{room_id, name}]}`, at most `MAX_LOGIN_ROOMS` (500), sorted by name. Served from memory. |
| `POST /api/auth/room-login` | Body `{room_id, password, surface}`. `room_id` is the room picked in the dropdown (the room is the "username"); `password` is the one event password. Sets the surface's cookie. Returns `RoomIdentity`. |
| `POST /api/auth/staff-login` | Body `{username, password}`. Sets `staff_sid`. Returns `StaffIdentity`. |
| `POST /api/auth/logout?surface=…` | Clears that surface's cookie. `204`. |
| `GET /api/me?surface=…` | Who am I on this surface? (Cookies are HttpOnly, so the UI asks.) Returns `RoomIdentity` or `StaffIdentity`; `401` if not logged in. |

- **Cookies:** opaque random session tokens, `HttpOnly; Secure; SameSite=Lax`. One cookie per surface so one laptop can hold several: `display_sid`, `control_sid`, `staff_sid`.
- **Lifetime:** room sessions last until the event is closed or the room password is rotated. Staff sessions last `STAFF_SESSION_TTL_H` (24 h) and can be revoked.
- **CSRF:** every `POST` must carry the header `X-Proctor-Client` with any non-empty value. Missing → `400 invalid_request`.
- **Login hardening:** logins are rate-limited per IP and per room (`429 rate_limited`; exact numbers are server config, not contract). Wrong credentials → `401 invalid_credentials`.
- **Wrong-room safeguard:** because the room is chosen from a dropdown, after login the UI **must** show the room name in very large text with "Is this your room?" before enabling anything. The staff dashboard shows connected device counts per room (Phase 2) so a mistaken login is visible.
- **What each cookie may do:**

| Cookie | Read own room (stream, snapshot) | Send commands | Staff endpoints |
|---|---|---|---|
| `display_sid` | yes | no | no |
| `control_sid` | yes | start, pause, resume (own room only) | no |
| `staff_sid` (admin, pm) | any room | permit, start, pause, resume, end, adjust (any room) | yes |
| `staff_sid` (to) | any room | none | yes (read) |

## 4. Clock sync

- `GET /api/time` → `{server_time_ms}`. No auth, no database. Reads the server clock only.
- Client algorithm (also in plan §3.5): record `t0 = performance.now()`; request; record `t1 = performance.now()`; the sample's server time at `t1` is `server_time_ms + (t1 − t0) / 2`. Keep the lowest-RTT sample of the last `CLOCK_SAMPLES_KEPT` (8). Re-sync every `CLOCK_RESYNC_INTERVAL_S` (60 s), on every reconnect, and on wake.
- `serverNow() = anchorServerTime + (performance.now() − anchorPerf)`. The wall clock is never used for timer math.
- **Sleep/wake:** on `visibilitychange`/resume, compare how far `Date.now()` and `performance.now()` advanced; if they differ by more than `CLOCK_JUMP_THRESHOLD_MS` (2000), re-sync. If offline, fall back to the wall-clock delta and show "time re-estimated".
- `server_time_ms` inside snapshots and heartbeats is **informational only**. It is not a sync sample, because the delivery delay is unknown.

## 5. Timer model

### 5.1 Statuses and events

Status ∈ `NOT_PERMITTED → PERMITTED → RUNNING ⇄ PAUSED → ENDED`. Event types: `PERMIT`, `START`, `PAUSE`, `RESUME`, `ADJUST`, `END`.

### 5.2 Snapshot fields and remaining time

`TimerSnapshot = {status, duration_ms, adjust_total_ms, elapsed_banked_ms, running_since_ms}`.

```
remaining(now) = max(0, duration_ms + adjust_total_ms − elapsed_banked_ms
                        − (status == RUNNING ? now − running_since_ms : 0))
```

Clients recompute `remaining(serverNow())` every `TIMER_TICK_MS` (250 ms). They never decrement a counter (invariant 4).

### 5.3 Effective time and order

- A **room** event takes effect at its `claimed_at_ms`. It is valid only if `session.created_at_ms ≤ claimed_at_ms ≤ received_at_ms`; otherwise it is rejected (`claimed_at_out_of_bounds`).
- A **staff** event takes effect at the server's `received_at_ms`. (Staff `claimed_at_ms` is ignored.)
- A **system** event (e.g. a logged expiry marker) is informational and ignored by the fold.
- The fold sorts by `(effective_time, received_at_ms, command_id)` and applies events in that order. Input list order never matters.

### 5.4 Transition rules

Before applying any event at effective time *t*: **if the session is RUNNING or PAUSED and `remaining(t) ≤ 0`, it is ENDED** (time ran out; no stored END is needed). Zero is inclusive. When a RUNNING timer expires, `elapsed_banked_ms` becomes `duration_ms + adjust_total_ms` and `running_since_ms` becomes `null`.

| Event | Valid when | Effect | Otherwise rejected as |
|---|---|---|---|
| `PERMIT` | `NOT_PERMITTED` | → `PERMITTED` | `already_permitted` |
| `START` | `PERMITTED` | → `RUNNING`, `running_since = t` | `not_permitted` (if `NOT_PERMITTED`) / `already_started` (if `RUNNING` or `PAUSED`) |
| `PAUSE` | `RUNNING` | bank `t − running_since`, → `PAUSED` | `not_running` |
| `RESUME` | `PAUSED` | → `RUNNING`, `running_since = t` | `not_paused` |
| `END` | `RUNNING` or `PAUSED` | bank if running, → `ENDED` | `not_started` |
| `ADJUST` | any non-ended status, `0 < \|delta_ms\| ≤ MAX_ADJUST_MS` (3 h, inclusive) | `adjust_total += delta_ms` | `adjust_out_of_range` |
| any | — | — | `session_ended` if the session is already ENDED |

Precedence: `claimed_at_out_of_bounds` first, then `session_ended`, then the table.

### 5.5 Merge behavior (what makes offline safe)

1. Late-arriving offline events are inserted at their effective time and the session is **re-folded**. Server and device adopt the new result.
2. `ADJUST` events add up, so their order never matters, and an admin's adjustment is never overwritten.
3. A transition that is invalid at its place in the sorted order is **kept in the log, marked rejected, with a reason**. It is never silently dropped. Rejected events appear in the staff "conflicts" list (Phase 2) and as a toast on the device ("1 offline action was superseded by PM action").
4. `END` (and a future "switch test") is final. Room events claimed after it are rejected; room events claimed before it still count (fixture 20).
5. Because `START` by a room and `START` on behalf by staff are the same event type, whichever has the earlier effective time wins and the other becomes `already_started` (fixture 18).
6. **Once time hits zero the session is over.** A later ADJUST is rejected with `session_ended`. (See open question Q1, §13.)

Every one of these rules is exercised by `contracts/timer-fixtures/`.

## 6. Commands

One endpoint: `POST /api/commands`, one command per request. Requires the cookie for the target room (or a staff cookie) and the `X-Proctor-Client` header.

### 6.1 Envelope (all commands)

| Field | Type | Notes |
|---|---|---|
| `type` | `permit \| start \| pause \| resume \| end \| adjust` | discriminator |
| `command_id` | UUID | generated by the client when the user acts; **reused on every retry** |
| `device_id` | UUID | stable per browser install |
| `room_id` | string | must be the cookie's room for room devices |
| `session_id` | string | the session the client believes is current |
| `claimed_at_ms` | int | client's `serverNow()` at the moment of the action; ignored for staff |
| `proctor_name` | string? ≤ 100 | optional free text, stored on the event |
| `reason` | string? ≤ 200 | optional (pause reason, adjustment reason) |
| `delta_ms` | int | `adjust` only; may be negative; range is checked by the fold, not the schema |

### 6.2 Who may send what

| Command | Room (`control`) | Admin | PM | TO |
|---|---|---|---|---|
| `permit` (grant permission to start) | no | yes | yes | no |
| `start` | yes (own room; valid only if PERMITTED) | yes (**on behalf of the room**) | yes (**on behalf**) | no |
| `pause`, `resume` | yes | yes (0.4.0) | yes | no |
| `end` (end early) | **no: proctors cannot end a test early** | yes | yes | no |
| `adjust` | no | yes | yes | no |

A command from someone not allowed to send it → `403 forbidden`, nothing recorded. "Start on behalf" is just `start` sent with a staff cookie; the stored event has `actor_kind = staff` and the staff account id, and takes effect at the server's receive time.

### 6.3 Response

`200 CommandResponse {command_id, outcome, reason, replayed, snapshot}`.

- `outcome = applied` → the event changed state (`reason = null`).
- `outcome = rejected` → the event was valid and authorized but could not be applied; `reason` is a `RejectionReason` (§5.4, plus `stale_session`). **It is still recorded** in the event log with status `rejected`.
- `snapshot` is the room's current snapshot after processing. The client adopts it.
- A rejected outcome is a normal `200`, not an HTTP error. Clients show it (e.g. "Already paused") and clear the command from the outbox.

### 6.4 Idempotency (invariant 3)

`command_id` is a unique key. Sending it again returns the original `outcome` and `reason` with `replayed: true` and the *current* snapshot. Sending the same `command_id` with different content → `409 command_id_conflict`. Retrying after a timeout or a lost response is always safe.

`stale_session`: if `session_id` is not the room's current session (a test switch happened), the command is rejected with `stale_session`.

### 6.5 HTTP errors (not recorded as events)

| Status | `error` | When |
|---|---|---|
| 400 / 422 | `invalid_request` | malformed body; missing `X-Proctor-Client` (400) |
| 401 | `unauthenticated` / `invalid_credentials` | no or bad cookie / wrong password |
| 403 | `forbidden` | role or room not allowed |
| 404 | `unknown_room` / `unknown_session` | id doesn't exist |
| 409 | `command_id_conflict` | see §6.4 |
| 429 | `rate_limited` | |
| 500 / 503 | `internal` / `unavailable` | clients treat as "server down" and use the backoff in §8 |

### 6.6 Server handling order (invariants 1, 5)

For each command: authenticate → authorize → lock the room → check `command_id` → append the event to Postgres and update `room_current` **in one transaction, and commit** → update memory, bump `version` → broadcast. A command never reads Postgres to decide anything except through the one write transaction.

## 7. Snapshots and streaming

### 7.1 RoomSnapshot

`{room_id, room_name, test_name, session_id, version, server_time_ms, timer: TimerSnapshot, deleted, doc_url}`. `deleted` rooms are only ever sent to staff. Always sent whole, so a client can never hold a half-updated state. About 2 KB.

### 7.2 Server-Sent Events

- `GET /api/rooms/{room_id}/stream` (room cookie for that room, or staff). `GET /api/staff/stream` (staff).
- On connect the server immediately sends the current snapshot (room stream) or one snapshot per room (staff stream), then one `snapshot` per change.
- Frames:

```
event: snapshot
id: 42
data: {"room_id": "…", "version": 42, …}

event: heartbeat
data: {"server_time_ms": 1760000000000}
```

- **Presence (0.4.0).** `GET /api/rooms/{room_id}/stream?surface=control|display` says which page is listening; it counts only if that surface's own login is valid for the room (a staff preview never counts). The staff stream also carries `event: presence` with `RoomPresence` (`control`/`display`: `online` = streams open now, `last_seen_ms` = last connect or disconnect, null = never since the server started): once per room with data on connect, then on every change. In memory only. A device that vanishes without closing is noticed within about one heartbeat.
- A room stream ends when its room is deleted; the device's next request gets 404 and it goes to login.
- A `heartbeat` is sent on every open stream every `HEARTBEAT_INTERVAL_S` (15 s).
- `id` equals the room version. Resuming with `Last-Event-ID` is not needed, since every frame is a full snapshot.
- Responses must not be buffered or compressed in a way that delays frames (Caddy is configured with `flush_interval -1`).

### 7.3 Polling fallback

`GET /api/rooms/{room_id}/snapshot?since_version=N` → `200 RoomSnapshot`, or `304` if the room's version is ≤ N. Served from memory. Used only when streaming fails (§8). Never returns an unbounded list (invariant 8).

### 7.4 Staff list

`GET /api/staff/rooms` → `{rooms: [RoomSnapshot]}`, at most `MAX_STAFF_ROOMS` (1000). Staff cookie only. Used for the dashboard's first paint.

## 8. Client network behavior (invariant 2)

Applies to every loop: clock sync, stream, polling, outbox flush.

- **One request in flight per loop**, every request with a `REQUEST_TIMEOUT_S` (10 s) timeout.
- **Full-jitter exponential backoff** after any failure: wait `uniform(0, min(BACKOFF_CAP_S, BACKOFF_BASE_S · 2^attempt))` seconds, `attempt` counting from 0 (cap 30 s). Reset `attempt` to 0 on success.
- **Stream liveness:** if nothing (snapshot or heartbeat) arrives for `STREAM_DEAD_AFTER_S` (35 s), treat the stream as dead.
- **Do not rely on the browser's automatic `EventSource` reconnect.** On any error, `close()` the stream and reconnect yourself with the backoff above.
- **Fallback:** after `SSE_FAILURES_BEFORE_POLLING` (3) consecutive stream failures, poll `snapshot?since_version=N` every `POLL_INTERVAL_S` (5 s) plus a uniform offset in ±`POLL_JITTER_S` (1 s), and keep trying to re-open the stream in the background.
- **Connectivity states:** *online* (stream alive), *degraded* (polling works), *offline* (nothing works). The display shows "last synced Ns ago"; amber when offline, red after `OFFLINE_RED_AFTER_S` (300 s).
- **On wake / visibility:** re-sync the clock, then reconnect immediately (reset backoff).

## 9. Offline behavior of room devices

- The display and control pages must load and keep time with the server down (invariant 7): Service Worker for the shell, IndexedDB for the last snapshot and the outbox.
- Allowed while offline (control surface): `start` (only if the local projection is PERMITTED), `pause`, `resume`. Everything else needs the server.
- Each action creates a command (new `command_id`, `claimed_at_ms = serverNow()`) saved in the **outbox** before anything else. The page shows the *local projection*: last server snapshot + outbox events replayed through the same fold.
- On reconnect, send the outbox **in order, one at a time**. When it is empty, adopt the latest server snapshot.
- A permission granted before the drop is already in the last snapshot, so a proctor can still press Start (plan §2.2b).

## 12. Not in v0 (reserved; add in later versions)

Bathroom log, clarifications, messages, practice-mode switching beyond the `?practice` flag, test sequences and "set current test"/"switch test" (and therefore session creation, which is seed/admin tooling in v0), batch commands (the dashboard sends one command per room), device presence and heartbeats from devices, the staff "conflicts" list endpoint, exports, account management endpoints, a global "go" signal. Each will be added as new endpoints/commands without changing anything above.

1. **Adding time after expiry.** Today, once the timer reaches zero the session is over and staff cannot add time (§5.5.6). If a proctor ends up needing "give them 30 more seconds" after a timer hit zero, a future `reopen` command would be needed. Decide before Oct 24 whether that is a Tier 1 need.
2. ~~**Staff pause/resume.**~~ Resolved in 0.4.0: admins and PMs can pause and resume any room.
3. **Dropdown size.** `GET /api/auth/rooms` is public and lists every room name (≤ 500). Accepted for v0 because the event password protects access, but it does reveal the room list to anyone who can reach the server.
